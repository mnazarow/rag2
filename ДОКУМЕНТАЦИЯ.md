# Ассистент корпоративной базы знаний

Отвечает сотрудникам в Telegram и по телефону на вопросы по папке с
документами: каталоги, паспорта, сертификаты, руководства, прайс-листы,
чертежи, фотографии, видеоинструкции и внутренние регламенты. Цитирует
источники, присылает файлы, принимает голосовые сообщения и отвечает
голосом, накапливает выверенные экспертами ответы.

Документ описывает методологию, установку, настройку и повседневную работу.
Справочник по каждому параметру — в файле `НАСТРОЙКИ.md`, он генерируется
из кода и всегда актуален.

---

## 1. Как это устроено

### 1.1. Общая идея

Система не «знает» ничего сама. Она ищет в ваших документах и отвечает
только по найденному. Это принципиально: справочный ассистент, который
додумывает недостающее, хуже отсутствия ассистента, потому что ошибку
никто не заметит.

Путь вопроса выглядит так. Сотрудник спрашивает в Telegram. Вопрос
проверяется по базе выверенных ответов — если эксперт уже отвечал на
похожий, отдаётся его ответ. Если вопрос о цене, он уходит в таблицу
прайсов с точным поиском по артикулу. В остальных случаях работает
поиск по документам: два независимых канала находят подходящие
фрагменты, их списки объединяются, лучшие передаются языковой модели
вместе с инструкцией отвечать только по ним. Ответ возвращается со
ссылками на документы, из которых он собран.

### 1.2. Почему два канала поиска

Первый канал — текстовый, он ищет по словам. На запросе «SPL WRP-A
2ECO6-38» или «арт. 500095.F» это единственный работающий способ:
никакая смысловая близость не поможет найти точную строку.

Второй канал — смысловой, он переводит текст в числовые векторы и ищет
близкие. На вопросе «чем скважинный насос отличается от колодезного»
работает только он: ни одно слово из вопроса может не встретиться
в нужном документе.

Списки объединяются методом взаимного ранжирования: документ, оказавшийся
высоко хотя бы в одном списке, попадает в итог. Метод не требует подбора
весов и стал отраслевым стандартом.

### 1.3. Почему цены отдельно

Смысловой поиск возвращает *похожие* строки. Похожая цена — это неверная
цена, и ошибка здесь стоит денег напрямую. Поэтому прайс-листы
разбираются в обычную таблицу «артикул — наименование — цена — дата», и
ценовые вопросы направляются туда точным поиском. Позиции подаются модели
отдельным блоком с пометкой, что это точные данные.

### 1.4. Почему у каждого фрагмента есть контекст

Документ режется на фрагменты — целиком он в модель не поместится. Но
фрагмент «Напор 45 м, расход 3,6 м³/ч» сам по себе не содержит ни бренда,
ни модели, ни даже указания, что речь о насосе. Найти его невозможно.

Поэтому к каждому фрагменту дописывается строка вида «Фрагмент документа:
Джилекс, паспорт, «Водомет 3ДК», раздел: Технические характеристики».
Она собирается из пути к файлу и заголовка раздела — бесплатно и всегда.

### 1.5. Почему нетекстовые файлы тоже находятся

Чертёж, фотография и видео для поиска невидимы. Решение: каждый такой
файл получает текстовую карточку — что это, какого бренда, из какой
товарной линейки, как называется, что лежит рядом в папке. Карточка
делает файл находимым и привязывает его к своей папке.

Дальше карточка обогащается: к видео добавляется расшифровка речи
с таймкодами, к фотографии — описание кадра и надписи с шильдика,
к чертежу — текст основной надписи. Это стоит времени и денег, поэтому
делается отдельным проходом и включается по необходимости.

### 1.6. Почему структура папок важна

Первый уровень папок внутри базы становится «разделом» и определяет права
доступа. Второй — «брендом». Третий, если он называется как известная
категория (`1КАТАЛОГ`, `4ПАСПОРТ`, `5СЕРТИФИКАТ`), задаёт тип документа.
Всё это извлекается автоматически и работает как фильтр при поиске.

Отсюда практическое требование: не переименовывать папки категорий
произвольно. Система следит за структурой и предупреждает, когда
появляется папка с незнакомым именем — документы в ней получат пустой тип.

### 1.7. Почему дата в имени файла критична

Определить, какой из двух прайсов свежее, по файловой системе нельзя:
при копировании папки все даты изменения становятся одинаковыми. Поэтому
дата берётся из имени файла. Распознаются все распространённые записи:
`PRICE 01.02.2026`, `price_300326`, `с 03-03-2026`, `Каталог 2023`.

Если по одному «ключу версии» найдено несколько документов, актуальным
остаётся самый свежий, остальные помечаются вытесненными и в выдачу не
попадают. Отсюда правило: **дату в имени прайса нужно ставить всегда**.

## 2. Установка

### 2.1. Что понадобится

| Что | Минимум | Рекомендуется |
|---|---|---|
| Процессор | 4 ядра | 8 ядер |
| Оперативная память | 8 ГБ | 16–32 ГБ |
| Диск | 50 ГБ | 200 ГБ и больше под модели |
| Видеокарта | не нужна | 2×RTX 4090 для локальных моделей |
| Python | 3.10 | 3.12 |
| Система | Linux, macOS, Windows | Linux |

Без видеокарты работает всё, кроме локальных моделей: поиск, бот,
админка, обход сайтов. Модели в этом случае берутся из облака.

### 2.2. Linux и macOS

```bash
cd assistant
./install/install.sh                    # обычная установка
./install/install.sh --with-gpu         # плюс библиотеки локальных моделей
./install/install.sh --docker           # в контейнерах
./install/install.sh --dry-run          # посмотреть, что будет сделано
./install/install.sh --no-service       # без автозапуска (запуск руками)
./install/install.sh --no-network       # веб-интерфейс только с этой машины
./install/install.sh --no-packages      # не ставить системные утилиты
```

Автозапуск и доступ из сети включены по умолчанию: скрипт регистрирует
службы админки и бота (systemd на Linux, launchd на macOS), открывает
веб-интерфейс наружу и заводит учётную запись **admin / admin**, если
записей ещё нет. Вход — по имени и паролю на странице входа; адрес вида
`http://адрес-машины:8800` печатается в конце установки. Пароль по
умолчанию известен всем, поэтому проверка перед стартом и оповещения
напоминают о нём, пока он не сменён (раздел «Безопасность» → «Сменить
свой пароль»). Отказаться: `--no-service` и `--no-network`.

Скрипт проверяет версию Python, доставляет недостающие системные
утилиты, создаёт окружение, ставит зависимости и готовит файл настроек.
Повторный запуск безопасен: сделанные шаги пропускаются.

Системные утилиты ставятся автоматически. Скрипт определяет пакетный
менеджер (`apt`, `dnf`, `pacman`, `zypper`, `brew`), пропускает то, что
уже есть, и вызывает `sudo` только если запущен не от root. Ставятся:

| Утилита | Зачем |
|---|---|
| `ffmpeg` | видео и голосовые сообщения |
| `poppler-utils` (`pdftotext`) | разбор PDF, если не встанет PyMuPDF |
| `libarchive-tools` (`bsdtar`) | распаковка архивов RAR |
| `git` | обновления через `update.sh` |
| `tesseract` + `tesseract-ocr-rus` | распознавание сканов сертификатов |

Сбой установки пакета не прерывает установку: скрипт печатает, что не
встало, и идёт дальше — без утилиты система работает, просто без части
возможностей. Доставить их можно позже и запустить установку повторно.

Если пакеты ставит администратор отдельно, передайте `--no-packages`:
скрипт только проверит наличие и покажет список недостающих.

```bash
# поставить руками, если хочется контролировать
sudo apt-get install -y ffmpeg poppler-utils libarchive-tools git \
                        tesseract-ocr tesseract-ocr-rus
brew install ffmpeg poppler libarchive git tesseract tesseract-lang   # macOS
```

### 2.3. Windows

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\install\install.ps1 -Dir C:\KBAssistant -Service
```

Ключи те же: `-Docker`, `-WithGpu`, `-DryRun`, плюс `-NoService`,
`-NoNetwork` и `-NoPackages` (автозапуск и доступ из сети, как и на
Linux/macOS, включены по умолчанию; без прав администратора автозапуск
не создастся — скрипт предупредит и продолжит). Системные утилиты скрипт ставит сам через `winget`
(`Gyan.FFmpeg`, `oschwartz10612.Poppler`, `Git.Git`,
`UB-Mannheim.TesseractOCR`). Если `winget` в системе нет, скрипт
напечатает готовые команды и продолжит установку.

Учтите: новые утилиты попадают в `PATH` только после перезапуска
терминала, поэтому проверка сразу после установки может показать их как
отсутствующие.

Отдельно про локальные модели на Windows: сервер `vllm` официально
Windows не поддерживает. Варианты — Ollama или запуск через WSL2.

### 2.4. Контейнеры

```bash
cp .env.example .env      # укажите KB_ROOT
docker compose up -d
docker compose exec app python index.py build
docker compose --profile gpu up -d      # плюс локальная модель
```

Папка базы знаний подключается только на чтение: ассистент никогда не
изменяет исходные документы.

### 2.5. Обновление и удаление

```bash
./install/update.sh                # с резервной копией
./install/update.sh --rollback     # вернуться к предыдущей версии
# если репозиторий склонирован отдельно от установки:
./install/update.sh --target /путь/к/установке --from /путь/к/репозиторию
./install/uninstall.sh             # удалить программу, данные сохранить
./install/uninstall.sh --all       # удалить всё
```

Перед обновлением автоматически сохраняются настройки, индекс и журналы;
хранятся пять последних копий. Папка базы знаний не трогается никогда.

## 3. Первый запуск

### 3.0. Быстрый старт в интерфейсе

Всё, что описано ниже, продублировано в разделе «Быстрый старт» — он
открывается первым. Там те же десять шагов, что печатает установщик, но
у каждого видно состояние, рядом лежат его настройки и стоит кнопка
запуска.

Смысл не в кнопках, а в состоянии. Установщик печатает список команд и
прощается; дальше человек не имеет способа понять, где он находится.
Шаги «проиндексировать базу» и «включить смысловой поиск» внешне
неразличимы: обе команды отрабатывают без ошибок, а при пропущенном
втором поиск находит только точные слова из документа. Вопрос, заданный
своими словами, остаётся без ответа — и обнаруживается это через неделю
по жалобе сотрудника, когда связать её с пропущенным шагом уже трудно.

Команды для терминала показаны у каждого шага и остаются полностью
рабочими: по SSH интерфейс недоступен, а делать одно и то же двумя
способами система должна одинаково. Есть проверка, которая следит, что
списки не разошлись: если установщик начнёт советовать команду, которой
нет в быстром старте, тест это покажет.


### 3.1. Указать путь к базе

Откройте `.env` и задайте `KB_ROOT` — путь к папке с документами.
Важно указать именно корень: имена разделов в правах доступа должны
совпадать с папками первого уровня.

### 3.2. Проиндексировать

```bash
venv/bin/python index.py build        # первый проход
venv/bin/python index.py stats        # что получилось
```

На базе в двенадцать тысяч файлов проход занимает от семи минут до
получаса в зависимости от диска. Прерывать безопасно: при повторном
запуске работа продолжится с того же места.

### 3.3. Включить смысловой поиск

Поиск работает по двум каналам. Текстовый находит точные слова и
артикулы. Смысловой находит ответ, когда вопрос задан не теми словами,
что написано в документе: «какая производительность» — а в паспорте
написано «подача, м³/ч». Без второго канала половина вопросов,
заданных живым языком, остаётся без ответа.

Смысловой канал нужно один раз включить:

```bash
venv/bin/python index.py train-lsa     # обучить модель на вашей базе, минуты
venv/bin/python index.py reembed       # пересчитать векторы
```

Первая команда обучает модель прямо на текстах вашего индекса: она
не требует интернета, весов и видеокарты, весит несколько десятков
мегабайт и обучается на базе в сорок тысяч фрагментов примерно за
полторы минуты. Вторая пересчитывает векторы — файлы при этом заново
не разбираются, поэтому это минуты, а не часы.

Проверить, что канал включился:

```bash
venv/bin/python ask.py --debug "какая производительность у скважинного насоса"
```

В отладочной выдаче у найденных фрагментов должен появиться канал
`dense`. Если его нет — смысловой поиск не работает, см. раздел 12.

Когда база заметно вырастет, модель стоит переобучить: слова,
появившиеся после обучения, ей неизвестны. Админка сама напомнит об
этом в разделе «База знаний», когда число фрагментов вырастет больше
чем на треть.

### 3.4. Проверить поиск

```bash
venv/bin/python ask.py "какой напор у Водомет 55/50"
venv/bin/python ask.py --debug "цена насоса ВИНТОВИК 3"
```

Ключ `--debug` показывает, какой канал нашёл каждый фрагмент и с какой
оценкой. Это главный инструмент разбора «почему бот ответил не то».

### 3.5. Открыть админку

```bash
venv/bin/python webui.py
```

Дальше всё делается там: настройки, модели, аудит базы, журналы,
диагностика. Раздел «Диагностика» показывает, что настроено, а что нет,
и что с этим делать.

### 3.6. Запустить бота

Получите токен у `@BotFather`, укажите в `.env` `TELEGRAM_BOT_TOKEN`,
`TELEGRAM_ALLOWED_IDS` (кто допущен) и `TELEGRAM_ADMIN_IDS` (кто получает
уведомления о плохих ответах). Свой идентификатор сотрудник узнаёт
командой `/whoami`.

```bash
venv/bin/python bot.py
```

## 4. Выбор моделей

### 4.1. Три варианта

**Облако.** Российские провайдеры: рублёвая оплата, закрывающие
документы, данные не покидают страну. Самый быстрый старт и самая низкая
стоимость при небольшой нагрузке.

**Свои модели.** Данные не покидают сервер вообще. Нужна видеокарта.
При двух картах RTX 4090 (48 ГБ видеопамяти) доступны модели на 32
миллиарда параметров.

**Смешанно.** Чувствительные разделы обслуживает локальная модель,
остальное — облако. Поддерживается той же архитектурой.

### 4.2. Что помещается в 48 ГБ видеопамяти

Полный список — в админке, раздел «Модели», там же указано, что
поместится на вашем железе. Кратко:

| Модель | Память | Русский язык |
|---|---|---|
| T-Pro 2.0 (32 млрд, Т-Банк) | 22 ГБ | отличный, токенизатор под кириллицу |
| Qwen3 32B | 21 ГБ | хороший, универсальная база |
| Qwen3 30B-A3B (смесь экспертов) | 20 ГБ | хороший, отвечает заметно быстрее |
| GigaChat3 20B-A3B (Сбер) | 14 ГБ | отличный, обучалась на русском |
| Gemma 3 27B | 19 ГБ | средний, есть лицензионные оговорки |
| Qwen3 14B | 10 ГБ | хороший, оставляет место под остальное |

Плюс модель поиска (3 ГБ), переранжирование (3 ГБ), модель зрения
(10 ГБ) и распознавание речи (4 ГБ). На двух картах помещается языковая
модель на 32 миллиарда вместе со всем остальным.

### 4.3. Установка модели

В админке: раздел «Модели» → «Скачать» → «Запустить». Система сама
скачает веса, подберёт параметры запуска под число карт и пропишет адрес
в настройки. Загрузка весов занимает от нескольких минут до получаса.

Из командной строки:

```bash
python models.py hardware              # что за железо
python models.py list --vram 48        # что поместится
python models.py info t-pro-2.0        # подробности
python models.py install t-pro-2.0     # скачать
python models.py serve t-pro-2.0       # запустить
python models.py status                # проверить
```

**Важно для России.** Площадка с моделями напрямую недоступна. Укажите
зеркало в настройке `HF_MIRROR` или настройте прокси, иначе загрузка не
пойдёт. То же касается Docker Hub при установке в контейнерах.

### 4.4. Сколько отдавать видеопамяти

Настройка `LOCAL_MODEL_GPU_FRACTION`. Если карты заняты только языковой
моделью — 0.90. Если на них же работают модель поиска, зрение и
распознавание речи — снижайте до 0.70, иначе при первом же длинном
запросе не хватит памяти.

Длина контекста `LOCAL_MODEL_CONTEXT` влияет на память сильнее, чем
кажется: увеличение с 32 до 128 тысяч токенов может съесть несколько
гигабайт. В промпт уходит около четырёх тысяч токенов, так что 32 тысячи
хватает с большим запасом.

### 4.5. Модель смыслового поиска

Это отдельная модель, не та, что формулирует ответ. Она превращает
текст в числа так, чтобы близкие по смыслу куски оказались рядом.

**Своя модель на вашей базе (`EMBEDDINGS_PROVIDER=lsa`).** Стоит по
умолчанию. Обучается за минуты на текстах вашего индекса, работает на
процессоре, ничего не скачивает. Понимает связи между словами, которые
реально встречаются в базе: «подача» и «производительность» окажутся
рядом, потому что стоят в одних и тех же паспортах. Ограничение
называем честно: слов, ни разу не встретившихся в базе, модель не
знает — синоним из чужого лексикона она не подскажет.

**Готовая модель без torch (`EMBEDDINGS_PROVIDER=onnx`).** Качество
выше. Нужны файлы модели, подготовленные на машине с интернетом:

```bash
pip install optimum[exporters]
optimum-cli export onnx --model deepvk/USER-bge-m3 ./user-bge-m3-onnx
```

Папку переносят на сервер и указывают `ONNX_MODEL_PATH` и
`ONNX_TOKENIZER_DIR`. Для моделей на SentencePiece (BGE-M3, XLM-R)
на сервере понадобится `pip install tokenizers` — это несколько
мегабайт, не полтора гигабайта torch.

**Через sentence-transformers (`local`).** То же самое, но с torch и,
желательно, с видеокартой. Имеет смысл, если модели уже установлены
для других задач.

**Облако (`gigachat`, `yandex`, `openai`).** Работает сразу, но каждый
кусок текста уходит наружу — при индексации это вся база целиком.

Провайдера можно менять когда угодно: файлы заново не разбираются,
достаточно `python index.py reembed --provider onnx`.

### 4.6. Переранжирование

Поиск отбирает кандидатов дёшево и приблизительно. Переранжирование
берёт первые двадцать и заново читает каждую пару «вопрос + фрагмент»
целиком, отвечая на один вопрос: отвечает ли этот фрагмент на этот
вопрос. Это тот шаг, который убирает частый случай — нужный документ
нашёлся, но оказался седьмым и в ответ не попал.

| Значение `RERANKER_PROVIDER` | Что нужно | Когда выбирать |
|---|---|---|
| `lexical` | ничего | по умолчанию: работает сразу, без моделей и интернета |
| `onnx` | файл модели, 2–3 ГБ | лучшее соотношение качества и задержки |
| `local` | torch + модель | если torch уже стоит |
| `openai` | внешний endpoint `/v1/rerank` | если реранкер поднят отдельным сервисом |
| `none` | — | отключить |

Встроенный лексический реранкер считает три вещи: какая доля значимых
слов вопроса покрыта фрагментом (с весом по редкости слова), насколько
кучно эти слова в нём расположены и совпал ли артикул дословно.
Последнее на технической базе — самый надёжный признак.

Настоящий кросс-энкодер готовится так же, как модель эмбеддингов:

```bash
optimum-cli export onnx --model BAAI/bge-reranker-v2-m3 ./reranker-onnx
```

и указывается в `RERANKER_ONNX_PATH`. Восьмимиллиардную версию брать
не стоит: около пяти секунд на запрос для чата неприемлемо.

`RERANKER_WEIGHT` определяет, насколько мнение реранкера перевешивает
оценку поиска. Единица означает «доверять только реранкеру» — тогда
пропадает приоритет свежести, и на вопрос про цену может всплыть прайс
позапрошлого года просто потому, что формулировка в нём ближе к
вопросу. Значение 0.8 оставляет реранкеру решающий голос, сохраняя
приоритет свежих документов.

Любой сбой реранкера — недоступная модель, таймаут, ошибка сети —
означает выдачу в исходном порядке, а не потерю ответа.

## 5. Обработка материалов

### 5.1. Что и как разбирается

| Тип | Что делается |
|---|---|
| PDF | Текст постранично. Если текстового слоя нет — документ помечается как скан и ждёт распознавания |
| Word, Excel, презентации | Текст, таблицы, заметки докладчика |
| Прайс-листы | Отдельно: разбор в таблицу с точным поиском по артикулу |
| Письма Outlook | Заголовки, тело, список вложений |
| Веб-страницы | Содержимое без навигации и рекламы |
| Архивы | Рекурсивная распаковка, содержимое индексируется как обычные файлы |
| Чертежи DWG | Текст из PDF-двойника, иначе конвертация в DXF |
| STEP, IGES | Заголовок с названием изделия — эти форматы текстовые |
| Изображения | Карточка, при включённом зрении — описание и надписи с шильдиков |
| Видео | Карточка, при включённом распознавании — расшифровка с таймкодами |

Всего поддерживается около пятидесяти расширений.

### 5.2. Обогащение

```bash
python media.py cad          # надписи с чертежей
python media.py transcribe   # расшифровка видео
python media.py describe     # описания фотографий
```

Каждая команда работает только с необработанными файлами, повторный
запуск ничего не переделывает. Ключ `--force` заставляет переделать.

### 5.3. Обновление базы

```bash
python watcher.py once       # один проход
python watcher.py run        # постоянное слежение
python watcher.py structure  # что изменилось в структуре папок
```

Слежение отслеживает две вещи. Содержимое файлов — по хэшу, поэтому
копирование и пересинхронизация облака лишней работы не вызывают.
И структуру каталогов: появление, исчезновение и переименование папок.
Об изменениях структуры администраторы получают уведомление в Telegram —
это важно, потому что структура определяет права доступа и тип документа.

Если установлен `watchdog`, изменения ловятся мгновенно. Без него
работает опрос — надёжнее на сетевых дисках, где события теряются.

### 5.4. Распознавание сканов

Сертификаты и декларации почти всегда лежат сканами — картинками без
текстового слоя. Для поиска таких документов не существует, а спрашивают
их чаще всего: их запрашивают контрагенты и тендерные площадки.

```bash
venv/bin/python ocr.py providers          # что доступно на этой машине
venv/bin/python ocr.py queue              # что ждёт распознавания
venv/bin/python ocr.py run --limit 20     # проба на двадцати документах
venv/bin/python ocr.py run                # весь остаток
venv/bin/python ocr.py check файл.pdf     # разобрать один файл и посмотреть текст
```

Это однократный прогон: распознанное сразу попадает в индекс и в поиск.

**Главное — подмена кириллицы латиницей.** Опасность русского OCR не в
пропущенной букве, а в том, что «МОСКВА» превращается в «MOCKBA», где
все буквы латинские. Текст выглядит правильным, а документ потерян
навсегда: по запросу «Москва» он больше не найдётся. То же самое
происходит с артикулами: «СП-45» становится «CП-45».

Защита работает в три приёма и включена по умолчанию
(`OCR_CYRILLIC_GUARD=1`):

1. Слова, где к русским буквам примешаны латинские двойники, чинятся
   сразу — направление подмены очевидно.
2. Слова, написанные целиком «латиницей-двойником», сверяются со
   словарём вашей же базы. Если такого слова в базе нет, а его русское
   прочтение есть — слово исправляется. Словарь берётся из обученной
   смысловой модели, поэтому распознавание лучше запускать после
   `index.py train-lsa`.
3. Если подозрительных слов на странице всё равно больше порога,
   страница переотправляется провайдерам из `OCR_FALLBACK`. Документ,
   у которого качество осталось низким, попадает в индекс, но остаётся
   в очереди: когда появится более точный распознаватель, его обработают
   заново.

Настоящие латинские названия — Grundfos, IP68, SP-45 — проверка не
трогает: в расчёт идут только буквы, неотличимые от русских.

**Выбор провайдера.**

| Значение | Что нужно | Замечания |
|---|---|---|
| `vlm` | зрительная модель по OpenAI-совместимому адресу | лучшее качество на печатях и таблицах, кириллица надёжнее всего; модель можно поднять на своих картах — тогда сканы не покидают периметр |
| `tesseract` | пакет `tesseract-ocr-rus` | бесплатно и офлайн; **без языкового пакета русский текст выйдет латиницей** — программа это проверяет и откажется работать |
| `yandex` | ключ Yandex Cloud | российский контур, хорошо держит кириллицу |

Языковой пакет ставится так:

```bash
sudo apt install tesseract-ocr tesseract-ocr-rus poppler-utils   # Debian, Ubuntu
brew install tesseract tesseract-lang poppler                    # macOS
```

Время работы: на трёхстах сканах по несколько страниц tesseract тратит
десятки минут, зрительная модель — часы, если она внешняя, и заметно
меньше на своих картах. Прогон можно прерывать: уже распознанное
сохранено, очередь продолжится с того же места.

## 6. Голос

### 6.1. Голосовые сообщения

Сотрудник присылает голосовое, бот распознаёт, отвечает и при
необходимости озвучивает ответ. Расшифровка всегда показывается текстом:
сотрудник должен видеть, что именно услышал бот, иначе непонятно, почему
ответ странный.

Настройки: `VOICE_STT_PROVIDER` — чем распознавать, `VOICE_TTS_PROVIDER` —
чем озвучивать, `VOICE_REPLY_MODE` — когда отвечать голосом. Значение
`on_voice` (голосом только в ответ на голосовое) — разумное по умолчанию:
в открытом офисе голосовые ответы раздражают, а цифры и артикулы на слух
не воспринимаются и не копируются. Сотрудник может переключить режим
командой `/voice`.

### 6.2. Подготовка текста к озвучиванию

Ни одна модель не прочитает «SPL WRP-A 2ECO6-38, Ду50 PN16, 3,6 м³/ч»
понятно. Поэтому перед синтезом текст проходит нормализацию: единицы
раскрываются словами, дробные числа читаются по-русски, буквенно-цифровые
обозначения проговариваются по частям. Проверить, как будет звучать
конкретный текст, можно в админке или командой:

```bash
python voice.py normalize "Насос SPL WRP-A 2ECO6-38, напор 45 м"
```

### 6.3. Голос по образцу

Технически поддерживается, но выключен, и это осознанно.

Голос человека относится к биометрическим персональным данным. Для
обучения модели нужно отдельное письменное согласие сотрудника, где
прямо сказано об использовании записи для синтеза речи — общей
формулировки о согласии на обработку персональных данных недостаточно,
что подтверждается судебной практикой. Отдельного закона об охране
голоса пока нет: законопроект был отправлен на доработку и с тех пор не
принят, но действующих норм о смежных правах исполнителя и о
биометрических данных достаточно для иска.

Кроме того, лучшие по качеству открытые модели клонирования
распространяются по некоммерческим лицензиям и в работе компании
применяться не могут.

Получив согласие и выбрав модель с подходящей лицензией:

```bash
python voice.py add-voice ivanov sample.wav --title "Голос Иванова" --consent
```

Образец — 15–30 секунд чистой речи без музыки и шума.

## 7. Телефония

Ассистент подключается к Asterisk двумя способами.

**Приложение Asterisk** (`SIP_MODE=ari`). АТС по правилу набора отправляет
звонок в наше приложение, звук ходит через AudioSocket. Рекомендуемый
путь: обмен событиями асинхронный и хорошо переносит задержки моделей.

**Обычный аппарат** (`SIP_MODE=sip`). Ассистент регистрируется на АТС
с логином и паролем. Подходит, когда доступа к настройке Asterisk нет.
Требует библиотеки `pjsua2`, которую нужно собирать.

Проверка настроек и готовая строка для `extensions.conf`:

```bash
python sip.py check
```

**О задержках честно.** Последовательная схема «распознали — подумали —
озвучили» даёт три-четыре секунды от конца фразы до начала ответа. Для
телефонного разговора это ощущается как зависание. Комфортным считается
интервал до восьмисот миллисекунд, и достигается он только потоковыми
движками. Поэтому в модуле предусмотрены реплики-заполнители вроде
«секунду, уточняю» — они закрывают паузу, пока идёт поиск.

## 8. Логирование

### 8.1. Как устроено

Пятнадцать подсистем, у каждой свой уровень подробности. Можно включить
детали только у поиска, не заливая журнал разбором документов. Уровни:
TRACE, DEBUG, INFO, WARNING, ERROR.

У каждого запроса есть сквозной номер: цепочка «вопрос в Telegram →
поиск → обращение к модели → ответ» видна целиком по одному номеру.

```bash
LOG_LEVEL_SEARCH=TRACE python ask.py "вопрос"   # подробности только по поиску
```

Уровни меняются на лету в админке, раздел «Журналы».

### 8.2. Что не попадает в журнал

Токены, ключи, пароли, телефоны, адреса электронной почты и IP-адреса
вырезаются автоматически. Это не паранойя: журналы часто пересылают
в переписке, и токен бота утекает именно так.

Полные тексты вопросов и расшифровок по умолчанию не пишутся — это
персональные данные. Включаются настройкой `LOG_PAYLOADS` на время
разбора конкретной проблемы.

### 8.3. Куда пишется

Файл `logs/assistant.log` с ротацией, отдельный `logs/errors.log`,
консоль и база (для показа в админке). Формат — человекочитаемый или
машинный, если журналы собираются во внешнюю систему.

«Конвейер».

## 10. Проверка качества

### 10.1. Аудит базы

```bash
python audit.py report
```

Восемь проверок: точные дубликаты, почти-дубли, документы-сироты без
смысловых связей, пробелы в покрытии (у какого бренда нет какого типа
документов), кандидаты на противоречие, распределение длин фрагментов,
документы, ни разу не попавшие в выдачу, полнота обработки нетекстовых
материалов.

Отчёт — это список задач для владельцев контента, а не для программиста.

### 10.2. Граф связности

```bash
python graph.py build --out graph.html
```

Один самодостаточный файл: узел — документ, линия — общая папка или
смысловая близость. Красным обведены документы без единой смысловой
связи, серым — вытесненные версии, оранжевым — сканы без распознавания.

### 10.3. Замер на контрольных вопросах

```bash
python evaluate.py --dataset eval/golden.jsonl --llm
```

Формат набора — одна строка на вопрос с указанием, какой документ должен
найтись. Без такого набора улучшать поиск вслепую невозможно: любое
изменение чанкинга или весов нужно мерить. Минимум — 50 вопросов,
рабочий объём — 150–300.

Кроме `expect_files` и `expect_text` набор понимает поля-запреты:
`reject_files` — документ, который считается ПОДМЕНОЙ, если стоит выше
нужного, и `reject_text` — подстрока, которой в ответе быть не должно.
Из них строятся «вопросы-двойники»: спрашиваем про модель 60/92 и
запрещаем в ответе цифры соседней 55/75. Только такие пары ловят самую
дорогую ошибку — когда система уверенно отвечает про другой товар.
Метрики `substituted` и `clean` показывают долю подмен.

Тот же набор ведётся из веб-интерфейса — раздел «Контрольные вопросы»:
эксперт добавляет вопросы без терминала, берёт кандидатов из журнала
неотвеченных, а помощник «двойник» превращает готовый вопрос в парный —
про соседнюю модель с запретами. Файл остаётся обычным `eval/golden.jsonl`:
его можно держать в git и переносить между установками.

Сам набор тоже проверяется:

```bash
python evaluate.py --audit
```

Аудит находит слишком общие шаблоны («4ПАСПОРТ» засчитывает паспорт
любого бренда — и подмену тоже), вопросы без ожидаемых цифр и
отсутствие пар-двойников. Метрика не лучше своих эталонов: набор со
слабыми эталонами показывает зелёные цифры при реальных ошибках.

Отдельный режим сравнивает настройки выдачи между собой на одном и том
же наборе:

```bash
python evaluate.py --dataset eval/golden.jsonl --compare
```

Он прогоняет набор без переранжирования и с ним при разных весах и
печатает таблицу. Ориентируйтесь на MRR: он учитывает не только
«нашлось ли», но и на каком месте. Это единственный честный способ
решить, включать ли переранжирование и с каким весом — на глаз такая
разница не видна.

Чтобы сравнить модели смыслового поиска, между прогонами нужно
пересчитать векторы:

```bash
python index.py reembed --provider lsa   && python evaluate.py --dataset eval/golden.jsonl
python index.py reembed --provider onnx  && python evaluate.py --dataset eval/golden.jsonl
```

Пересчёт занимает минуты — файлы заново не разбираются.

### 10.4. Резервное копирование индекса

Файлы базы знаний никуда не денутся — их можно разобрать заново.
Невосстановимо другое: выверенные ответы, накопленные вопросы
сотрудников и обучающие пары. Пересборка вернёт тексты, но не вернёт
ни одного выверенного ответа. Плюс сама пересборка — это часы, в
течение которых ассистент не работает.

```bash
venv/bin/python backup.py create        # снимок и сразу проверка
venv/bin/python backup.py list          # что есть
venv/bin/python backup.py schedule      # регулярный запуск средствами системы
venv/bin/python backup.py verify        # проверить последнюю копию
venv/bin/python backup.py restore data/backups/index-20260725-033000.tar.gz
```

В снимок попадают база индекса, векторы, обученная смысловая модель,
выверенные ответы и обучающие пары. Снимок базы делается средствами
самой SQLite, а не копированием файла: копия остаётся целостной, даже
если в этот момент идёт индексация. Обычное копирование под нагрузкой
даёт битый файл, который выглядит целым, — и выясняется это в тот день,
когда он понадобился.

Каждая копия сразу же проверяется: разворачивается во временную папку,
база открывается, считаются документы, фрагменты и векторы, сверяется
число векторов с числом идентификаторов. Копия, которую ни разу не
пробовали восстановить, — это ещё не копия.

При восстановлении текущее состояние не удаляется, а откладывается
рядом в папку `before-restore-…`. Если развернули не ту копию, откат
займёт минуту.

Хранение работает по правилу «дед — отец — сын»: ежедневные копии за
последнюю неделю, затем по одной за неделю, затем по одной за месяц.
Самая свежая копия не удаляется никогда. Настраивается параметрами
`BACKUP_KEEP_DAILY`, `BACKUP_KEEP_WEEKLY`, `BACKUP_KEEP_MONTHLY`.

Обязательно заполните `BACKUP_MIRROR_DIR` — вторую папку на другом
диске или в сетевом хранилище. Копия на том же диске не спасает от
отказа этого диска.

Расписание ставится командой `backup.py schedule`: на Linux и macOS
через `crontab`, на Windows через планировщик задач. Проверить:
`crontab -l` или `schtasks /query /tn KBIndexBackup`. В админке то же
самое делается кнопкой в разделе «База знаний», там же видно, когда
была последняя копия и прошла ли она проверку.

## 11. Как система становится точнее

Четыре независимых контура, от самого дешёвого к самому дорогому.

**Новые файлы подхватываются сами.** Слежение обходит папку, сверяет хэши
и переиндексирует только изменённое.

**Обратная связь.** Кнопки 👍 и 👎 под каждым ответом. Отрицательная
оценка уходит уведомлением экспертам, а пары «вопрос — показанный
фрагмент» копятся для будущего дообучения.

**Выверенные ответы — главный механизм.** Эксперт пишет в боте
`/expert вопрос | ответ` или добавляет ответ в админке. С этого момента
на похожие вопросы отдаётся именно он. Система перестаёт ошибаться там,
где ошиблась однажды. Это самый дешёвый способ и он даёт наибольший
эффект.

**Дообучение модели поиска.** Когда накопится несколько тысяч
подтверждённых пар, на них дообучается модель, превращающая текст
в векторы. По опубликованным замерам это даёт около семи процентов
прироста точности и стоит копейки. Дообучать языковую модель ради знания
фактов бессмысленно: факты устаревают, их место в базе, а не в весах.

Пробелы видны по команде `/gaps` и в разделе «Запросы»: вопросы, на
которые бот не ответил, — это готовый список задач на пополнение базы,
составленный на основании реальных потребностей сотрудников.

## 12. Что делать, если

**Бот отвечает «в базе нет данных» на вопрос, ответ на который есть.**
Проверьте `python ask.py --debug "вопрос"`. Если документ находится, но
оценка ниже порога — снизьте `MIN_CONFIDENCE`. Если не находится вовсе —
возможно, это скан без распознавания: посмотрите `python index.py ocr-queue`.

**Вопрос, заданный своими словами, не находится, хотя документ есть.**
Скорее всего не включён смысловой канал. Проверьте `python ask.py --debug`:
если у фрагментов нет канала `dense`, выполните `python index.py train-lsa`
и затем `python index.py reembed`. В админке то же самое видно в разделе
«База знаний» → «Качество поиска».

**После пополнения базы поиск стал хуже находить новые темы.** Смысловая
модель обучена на прежнем содержимом и новых слов не знает. Переобучите:
`python index.py train-lsa && python index.py reembed`. Админка сама
предупреждает об этом, когда база выросла больше чем на треть.

**Распознанный скан выглядит правильно, но не находится по русским
словам.** Классическая подмена кириллицы латиницей. Убедитесь, что
`OCR_CYRILLIC_GUARD=1`, и переобработайте документ:
`python ocr.py run --retry-failed`. Если распознаёте через tesseract —
проверьте, что установлен пакет `tesseract-ocr-rus`
(`python ocr.py providers` покажет).

**Переранжирование не работает.** `python -c "import rerank; print(rerank.describe())"`
покажет причину: не найден файл модели, нет библиотеки, недоступен
внешний адрес. Поиск при этом продолжает работать без него — ответы
не теряются, только выдача менее точная.

**Бот называет неверную цену.** Проверьте, нет ли в базе двух прайсов
одного поставщика без дат в именах. Команда `python audit.py report`
покажет кандидатов на противоречие.

**Ответы вообще не находятся, хотя индекс построен.** Скорее всего, имена
в `ROLE_SECTIONS` не совпадают с папками первого уровня внутри `KB_ROOT`.
`python index.py stats` предупреждает о таком несоответствии.

**Индексация идёт очень медленно.** Проверьте, что `DATA_DIR` находится
на локальном диске, а не в сетевой или примонтированной папке.

**Поиск по именам папок ничего не находит на macOS.** Это известная
особенность: система хранит имена файлов в форме, где «Й» записана двумя
символами. В коде нормализация есть; если пишете свои скрипты — учитывайте.

**Не скачиваются модели.** Площадка недоступна из России напрямую.
Укажите зеркало в `HF_MIRROR` или настройте прокси.

**Не хватает видеопамяти при запуске модели.** Снизьте
`LOCAL_MODEL_GPU_FRACTION` или `LOCAL_MODEL_CONTEXT`, либо выберите
модель поменьше — в разделе «Модели» видно, что поместится.

**Telegram недоступен.** Укажите прокси в `TELEGRAM_PROXY`. Поддерживаются
socks5 и http, с логином и паролем. Для socks5 нужен пакет `httpx[socks]`.

## 13. Что нужно от компании

Техника работает сама, но два контура требуют людей.

Нужен человек, который раз в неделю просматривает список неотвеченных
вопросов и жалоб — это примерно час времени. И нужны один-два эксперта
по направлениям, готовые писать выверенные ответы на повторяющиеся
вопросы. Без этих ролей система останется на уровне «неплохой поиск»,
но не станет точнее со временем.

Отдельно — порядок в базе. Дата в имени прайса, одна каноническая папка
на документ, устаревшее в архив за пределами рабочих папок. Это дешевле
любого алгоритма и работает надёжнее.

## 14. Аналитика и разбор ответов

### 14.1. Воронка ответа

Показывает путь вопроса от «задан» до «оценён» и потери между ступенями.
Читать её нужно именно по потерям.

Потеря на ступени «что-то нашлось» означает пробел в базе или в поиске —
дальше смотреть в группы вопросов без ответа. Потеря на «уверенность выше
порога» означает либо завышенный порог, либо что поиск приносит не то.
Потеря на «модель ответила» — сбои провайдера, их видно в журнале `llm`.
Отсутствие оценок означает, что качество никто не подтверждает, и все
выводы о нём — догадки.

```bash
python analytics.py funnel --hours 720
```

### 14.2. Гистограмма уверенности

Прямой инструмент подбора `MIN_CONFIDENCE`. На гистограмме почти всегда
видны два скопления: слева случайные совпадения, справа настоящие
находки. Порог ставится во впадину между ними.

Столбцы раскрашены по оценкам сотрудников: зелёное — «полезно», красное —
«неверно». Ниже — таблица «что было бы при другом пороге»: сколько
вопросов отсеклось бы и сколько из них на самом деле были полезными.
Отсечь полезный ответ — самая дорогая ошибка порога, потому что заметить
её невозможно: сотрудник просто получает «в базе нет данных».

```bash
python analytics.py confidence
```

### 14.3. Вклад каналов

Отвечает на вопрос, который иначе решают наугад: нужна ли более сильная
смысловая модель. Если заметная доля ответов приходит только из
смыслового канала — да, более сильная модель даст ещё прирост. Если почти
всё приносит текстовый канал — нет, и деньги на модель тратить незачем.

```bash
python analytics.py channels
```

### 14.4. Чего не хватает в базе

Вопросы без ответа и оценённые как неверные группируются по темам.
Список из двухсот отдельных вопросов бесполезен; «двадцать три вопроса
про подбор частотного преобразователя» — уже понятно, какой документ
нужен. Группы выгружаются списком для владельцев контента.

Группировка объяснимая, без моделей: вопросы связываются по общим
значимым словам, вес слова тем выше, чем оно реже.

```bash
python analytics.py gaps
```

### 14.5. Разбор конкретного ответа

Средние показатели не отвечают на вопрос «почему бот ответил вот это».
Для этого сохраняется полная цепочка: что нашёл каждый канал с какими
оценками, что переранжирование сделало с порядком, какой текст ушёл в
модель, что она вернула, и какие настройки действовали в тот момент.

```bash
python tracing.py list          # последние цепочки
python tracing.py bad           # только отказы
python tracing.py show 42       # одна целиком
python tracing.py find "гарантия"
```

В админке это раздел «Запросы»: кнопка «разобрать» рядом с каждым
вопросом, и оттуда же ответ можно сделать выверенным одним нажатием.

Цепочки живут в базе телеметрии с ограниченным сроком хранения: в них
попадает текст вопроса и куски документов, поэтому хранить их бессрочно
неправильно. Настройки — `TRACE_ENABLED`, `TRACE_KEEP`, `TRACE_PROMPT`.

### 14.6. Автоматические проверки качества

Контрольные вопросы прогоняются после переиндексации и смены настроек,
результат сохраняется вместе со слепком настроек. На вопрос «после чего
стало хуже» появляется точный ответ.

```bash
python regression.py run --reason "после переиндексации"
python regression.py history
python regression.py diff
```

`diff` показывает не только изменение средних, но и то, что важнее:
список вопросов, которые перестали находиться. Средние могут почти не
измениться, а конкретный сценарий при этом сломаться.

## 15. Очередь задач и доступ сотрудников

### 15.1. Очередь длительных операций

Индексация, распознавание, обучение модели и пересчёт векторов идут
через очередь. Это даёт две вещи.

Очередь переживает перезапуск: задача, прерванная посередине, помечается
как оборванная и ставится заново одной кнопкой. Раньше перезапуск
процесса терял работу без следа.

И, что важнее, две задачи, которые пишут в одно и то же, одновременно не
выполняются. Два пересчёта векторов писали бы в один файл, и результат
выглядел бы целым, а на деле был бы испорчен. Теперь вторая попытка
получает понятный отказ с указанием, какая задача мешает.

```bash
python jobs.py list
python jobs.py retry 17
python jobs.py cancel 18
```

### 15.2. Доступ сотрудников

Незнакомый человек, написавший боту, получает отказ и предложение
оставить заявку командой `/request`. Заявка приходит администраторам в
Telegram и появляется в разделе «Сотрудники»: видно имя, ник, когда
обратился и что написал. Доступ выдаётся вместе с ролью — она определяет,
какие разделы базы человек увидит.

Отдельно различаются «отказано» и «заблокирован»: отклонённый может
подать заявку заново с пояснением, заблокированный — нет.

Список `TELEGRAM_ALLOWED_IDS` продолжает работать и имеет приоритет: он
удобен для первичной настройки, когда админки ещё нет под рукой. Но как
только людей становится больше пяти, поимённая выдача через админку
удобнее: у каждого доступа видно, кто и когда его выдал.

### 15.3. Журнал действий администратора

Восстановление из копии, полная переиндексация, смена порога отказа,
выдача доступа — всё это меняет поведение системы для всех сразу.
Каждое такое действие записывается с автором, временем и параметрами;
журнал виден в разделе «Аналитика».

## 16. Экран настроек и проверка значений

### 16.1. Всё в одном месте

Раздел «Настройки» содержит **все** параметры системы — на сегодня их
202 в 25 разделах. Не «основные», не «часто используемые»: если
параметром можно управлять, он есть на этом экране. Ходить на сервер и
править файл руками не нужно ни для чего, включая ключи провайдеров.

У каждой настройки четыре вещи, а не одно поле ввода: что она делает,
рекомендация — как её выбирать и почему именно так, пример значения и
значение по умолчанию. Всё это лежит в одном файле `settings_schema.py`,
откуда строится и форма в админке, и справочник `НАСТРОЙКИ.md`, и
образец `.env.example`. Поэтому справочник и экран не могут разойтись —
это один источник, а не три копии.

Сверху — сводка: сколько всего настроек и сколько изменено относительно
умолчаний. Второе число важнее первого. В реальной установке меняют
примерно десяток настроек из двух сотен, и именно они объясняют, почему
система ведёт себя не так, как у всех остальных. Флажок «только
изменённые» показывает этот десяток; у каждой изменённой настройки есть
кнопка «Вернуть по умолчанию», чтобы не искать исходное значение в
документации.

Ряд ссылок под сводкой — разделы со счётчиками: сколько в разделе
настроек и сколько из них изменено. Там же поиск сразу по названию,
ключу, описанию и рекомендации: если помните только, что «что-то было
про перебивание в телефонии», найдётся по слову «перебивать».

Для настроек с числовым диапазоном рядом с полем написано, что вообще
допустимо и что считается обычным. Показывать границу после отказа
поздно — правильнее видеть её до того, как значение введено.

Часть разделов дублирует свои настройки у себя: настройки поиска — в
«Качестве поиска», распознавания — в «Сканах», копий — в «Копиях»,
очереди — в «Моделях». Это те же карточки с тем же описанием, просто
рядом с кнопками, которыми ими пользуются.

### 16.2. Ключи и пароли

Ключи настраиваются здесь же, но обращение с ними отличается в двух
местах.

Значение ключа никогда не отдаётся в браузер. В поле всегда пусто, а
рядом написано, задан ключ или нет. Причина простая: пароль, приехавший
на страницу, оказывается в памяти вкладки, в отладчике и в сохранённой
копии страницы — а показывать его всё равно незачем. Пустое поле поэтому
означает «не трогать», а не «стереть»; для стирания есть отдельная
кнопка с подтверждением.

Ключи не пишутся в `.env`. Они уходят в отдельный файл с правами 600,
который не входит ни в архив обновления, ни в резервную копию. Раньше
это можно было отменить, не заметив: ключи выносили в защищённый файл
кнопкой, а первое же сохранение настроек из браузера возвращало их
обратно в `.env`. Теперь форма сама разделяет одно и другое, и на это
есть проверка в тестах.

### 16.3. Проверка значений

Значения проверяются на сервере при сохранении, теми же правилами и из
админки, и из командной строки. Проверяется четыре вещи: тип, допустимый
список для перечислений, диапазон и связи между настройками.

Последнее — самое ценное. Выбрать провайдер `onnx` и не указать путь к
модели легко, а обнаруживается это только при первом поиске. Такие связи
описаны явно, и сохранить противоречивый набор нельзя.

Ошибка означает «так сохранять нельзя, модуль не запустится».
Предупреждение — «необычно, но допустимо»; такое сохраняется после
подтверждения. Подсказка появляется прямо во время правки, не дожидаясь
нажатия «Сохранить».

### 16.4. Когда изменение начинает действовать

Часть настроек применяется сразу: после сохранения перечитываются модули
поиска, переранжирования, генерации, очереди к модели и безопасности.
Остальное вступает в силу при следующем запуске соответствующего модуля.

Одна тонкость, из-за которой это долго работало не так, как написано.
Настройки читаются из окружения процесса, а `.env` при запуске в это
окружение загружался «только если значения ещё нет». В результате первое
прочитанное значение оставалось навсегда: админка сохраняла новое,
честно писала в журнал «перечитаны модули», а модули продолжали работать
со старым. Со стороны это выглядит как «настройка ни на что не влияет»,
и её меняют ещё раз, и ещё. Теперь загрузчик различает, что пришло из
файла, а что задано снаружи — в systemd, docker-compose или командной
строке. Своё, прочитанное из файла в прошлый раз, он обновляет; заданное
снаружи не трогает, потому что для контейнера переданное ему значение
главнее файла из образа.

## 17. Кто отвечает на вопросы: локальная модель и облако

### 17.1. Два варианта и почему нужны оба

Локальная модель работает на ваших картах. Вопросы сотрудников и
содержимое документов не покидают сервер, за токены платить не нужно,
и никакой внешний сервис не может закрыться или подорожать. Цена —
видеокарты, которые кто-то должен обслуживать, и то, что при перезагрузке
сервер модели надо поднять заново.

Облако запускается сразу и не требует ничего, кроме ключа. Но каждый
вопрос уходит наружу и стоит денег.

Поэтому провайдер задаётся не одним значением, а цепочкой: основной плюс
запасные.

```
LLM_PROVIDER=local
LLM_FALLBACK=gigachat
```

Если локальная модель не ответила — не поднялась после перезагрузки,
кончилась видеопамять, зависла, — ассистент не замолкает, а отвечает
следующим в цепочке. Переключение пишется в журнал и видно в разделе
«Модели»: молча переехать на другого провайдера система не должна,
потому что при этом меняются и стоимость, и то, куда уходят данные.

Обратный порядок тоже осмыслен: облако основным, локальная модель
запасной — на случай, когда пропал интернет или кончились деньги на счету.

### 17.2. Запуск локальной модели

В разделе «Модели» видно, что помещается в вашу видеопамять. Рядом с
каждой моделью кнопка «Проверить»: она заранее говорит, что помешает —
не установлен vllm, не хватает видеопамяти, нет места на диске, не задано
зеркало для загрузки весов. Узнавать об этом через полчаса ожидания
неправильно.

```bash
python models.py list                # что поместится
python models.py install t-pro-2.0   # скачать веса
python models.py serve t-pro-2.0     # поднять сервер
```

После запуска настройки прописываются сами: `LLM_PROVIDER=local`.
Адрес при этом никуда не записывается — провайдер `local` спрашивает его
у запущенного сервера. Благодаря этому перезапуск модели на другом порту
ничего не ломает; раньше это была самая частая причина «модель работает,
а ассистент молчит».

Для двух RTX 4090 (48 ГБ) рекомендуется T-Pro 2.0 на 32 миллиарда
параметров: Apache 2.0, лучший русский среди помещающихся. Полный список
с требованиями — в разделе «Модели».

### 17.3. Проверка

Кнопка «Проверить живым запросом» задаёт модели короткий вопрос и
показывает, за сколько она ответила и что именно вернула. Одно дело
«настройки заполнены», другое — «модель действительно отвечает»; разница
обычно обнаруживается в самый неподходящий момент.

### 17.4. Очередь запросов к модели

Видеокарта выполняет запросы по одному в любом случае. Вопрос лишь в
том, где образуется очередь — у вас или внутри сервера модели.

Без очереди десять одновременных вопросов уходят на сервер разом. Он
берёт их все, делит видеопамять на десять частей и отвечает на каждый в
десять раз медленнее. Быстрого ответа не получает никто, хотя первый
спросивший мог бы получить его сразу. А если видеопамяти не хватило,
сервер модели падает и не отвечает уже никому.

С очередью первый вопрос обрабатывается на полной скорости, остальные
ждут. Суммарное время то же самое, но первый ответ приходит сразу, и
падений не происходит. Поэтому по умолчанию стоит один одновременный
запрос:

```
LLM_MAX_CONCURRENT=1        # одновременных запросов к модели
LLM_QUEUE_MAX=20            # сколько может ждать в очереди
LLM_QUEUE_TIMEOUT=120       # сколько ждать своей очереди, секунд
LLM_QUEUE_SLOT_TTL=300      # когда занятое место считается брошенным
LLM_QUEUE_SHARED=1          # очередь общая для всех процессов
```

Через очередь проходят **все** обращения к модели: вопросы из чата и
телефонии, распознавание сканов зрительной моделью, фоновая обработка
базы и даже проверка связи из админки. Единая точка входа сделана не
ради порядка, а по необходимости: ограничение, которое можно обойти,
забыв про него в новом месте кода, не ограничивает ничего.

**Очередь общая для всех процессов.** Админка, Telegram-бот и фоновые
задания — это разные процессы, и ограничение внутри одного из них не
остановило бы остальные. Именно межпроцессный случай самый опасный:
пересчёт смысловых приставок идёт по десяткам тысяч фрагментов часами и
без общей очереди занял бы модель целиком, пока сотрудник ждёт ответа в
чате. Согласование идёт через служебную базу — тем же способом, что и
очередь длительных операций, и по той же причине: переживает перезапуск
и не требует отдельного демона.

**Живой вопрос обгоняет фоновую работу.** Честный порядок «кто встал,
тот и первый» здесь был бы вреден: пакетное задание встаёт в очередь
сорок тысяч раз подряд, и сотрудник ждал бы конца всего прогона.
Поэтому у запроса есть важность: вопрос из чата и звонок — срочные,
обработка базы и распознавание сканов — фоновые. Внутри одной важности
порядок обычный, по времени.

**Отказ приходит сразу, а не в конце ожидания.** Если очередь длиннее
`LLM_QUEUE_MAX`, ответ приходит немедленно: модель занята, попробуйте
позже — и вместе с ним наиболее подходящие фрагменты базы, чтобы человек
хотя бы увидел, где искать. Две минуты ожидания и та же ошибка в конце —
худший из возможных вариантов.

**Место, занятое погибшим процессом, освобождается само** — через
`LLM_QUEUE_SLOT_TTL`. Поэтому этот срок должен быть заметно больше, чем
ожидание ответа модели: при `LOCAL_LLM_TIMEOUT=180` правильное значение
— 300. Проверка настроек это контролирует и не даст сохранить обратное
соотношение: место, освобождающееся раньше, чем модель успевает
ответить, снимает ограничение именно на долгих ответах, ради которых оно
и нужно. Скрипт обновления снимает оставшиеся места сам, чтобы после
перезапуска не ждать этот срок впустую.

Что видно в разделе «Модели»: кто выполняется и кто ждёт прямо сейчас, с
указанием источника и времени ожидания; за сутки — число запросов,
отказов, среднее ожидание в очереди, ожидание у худших пяти процентов и
среднее время самого запроса к модели. Разделение «ожидание в очереди»
и «время запроса» здесь главное: именно оно отвечает на вопрос,
поднимать ли `LLM_MAX_CONCURRENT`.

Из командной строки:

```bash
python llm_queue.py status     # кто выполняется и кто ждёт
python llm_queue.py stats      # ожидание и отказы за сутки
python llm_queue.py clear      # снять зависшие места (после аварии)
```

**Как подбирать значение.** Начните с единицы. Если в статистике много
отказов и большое ожидание — поднимите на один и посмотрите, не выросло
ли *время самого запроса*. Если оно выросло примерно во столько же раз,
во сколько увеличили, выигрыша нет: карта уже загружена полностью, надо
вернуться назад. Для облачного провайдера очередь не нужна вовсе —
поставьте `0`, ограничение снимется, а учёт сохранится.

## 18. Безопасность

### 18.1. Вход в администрирование

Пока учётных записей нет, действует прежнее правило: общий токен
`ADMIN_TOKEN`, а если и его нет — доступ только с локального адреса.
Как только заведена первая запись, включается вход по логину и паролю.

Ролей три. `viewer` — только смотреть: статистика, журналы, диагностика.
`operator` — плюс запускать задачи: индексация, распознавание, копии.
`admin` — плюс менять настройки, восстанавливать индекс из копии,
выдавать доступ сотрудникам. Различать их важно: «посмотреть статистику»
и «откатить индекс на неделю назад» — действия очень разного веса.

```bash
python -c "import security; security.add_user('ivanov','пароль','admin','Иван Иванов')"
```

Пароли хранятся не в открытом виде: PBKDF2 со ста тысячами итераций из
стандартной библиотеки. Неудачные попытки входа пишутся в журнал с
адресом, а ответ задерживается на секунду — чтобы подбор пароля не был
бесплатным.

### 18.2. Ключи и токены

Ключи выносятся из `.env` в отдельный файл с правами 600. Разница
существенная: `.env` попадает в архив обновления и в копии, а этот файл
нет. Кнопка «Вынести ключи в защищённый файл» в разделе «Безопасность»
делает это одним нажатием, заменяя значения в `.env` пометкой.

Шифровать файл своими силами здесь было бы самообманом: ключ шифрования
пришлось бы держать рядом. Правильный путь — внешнее хранилище, и для
него есть настройка `SECRETS_CMD`: любая команда, печатающая `KEY=VALUE`.
Через неё подключается vault, менеджер паролей или systemd-credentials.

### 18.3. Ограничение частоты обращений

Один сотрудник не должен иметь возможности израсходовать месячный бюджет
на модель за вечер. Пределы задаются на человека в час, на человека в
сутки и на всех сразу. Администраторы не ограничиваются. При превышении
сотрудник получает понятное сообщение, а не молчание.

### 18.4. Защита от подмены инструкций

Сотрудник может прислать сообщение, составленное так, чтобы бот
проигнорировал свои правила — например, выдал содержимое раздела, к
которому у него нет доступа.

Мер две. Первая: подозрительные обороты в вопросе не отклоняются, а
обезвреживаются — вопрос передаётся модели как цитата, с прямым
указанием, что внутри кавычек текст пользователя, а не инструкции.
Отклонять нельзя: формулировка «забудь про Grundfos, меня интересует
Wilo» совершенно нормальна.

Вторая мера важнее: готовый ответ проверяется на то, что в нём не
оказалось фрагментов из недоступных сотруднику разделов. Она смотрит на
результат, а не на формулировку, и поэтому ловит утечку независимо от
того, каким способом её добились. Если утечка обнаружена, ответ
заменяется отказом, а случай пишется в журнал как ошибка.

### 18.5. Срок хранения данных

Тексты вопросов — персональные данные. Хранить их бессрочно нельзя ни по
закону, ни по здравому смыслу.

```bash
python retention.py status            # что и сколько хранится
python retention.py clean             # удалить просроченное
python retention.py forget 12345      # удалить всё об этом сотруднике
python retention.py anonymize --days 90   # стереть связь вопросов с людьми
```

Выверенные ответы и обучающие пары не удаляются никогда: это результат
работы экспертов, а не переписка. Обезличивание — отдельная возможность:
если статистика пробелов в базе нужна, а связь с человеком нет,
идентификаторы стираются, а тексты остаются.

## 19. Оповещения и регулярные задания

### 19.1. Что сообщается

Раз в час проверяется восемь вещей, и каждая соответствует событию,
после которого нужно что-то сделать: нет свежей резервной копии,
кончается место на диске, не работает смысловой поиск, недоступна модель
генерации, ассистент отвечает запасным провайдером, растёт очередь
распознавания, много отказов за сутки, задачи завершились с ошибкой,
заявки на доступ ждут решения, ключи лежат в открытом виде.

Когда делать нечего, оповещений нет: система, которая шлёт сообщения
постоянно, перестаёт читаться через неделю. Повторные напоминания об
одном и том же приходят не чаще раза в `ALERT_REPEAT_HOURS`, а
починившееся закрывается само.

```bash
python alerts.py list     # что сейчас не так, без отправки
python alerts.py check    # проверить и сообщить
python alerts.py test     # убедиться, что сообщения доходят
```

### 19.2. Расписание

```bash
python schedule.py install    # поставить все задания
python schedule.py status     # что настроено
```

Ставится пять заданий, каждое со своей причиной: резервная копия ночью,
когда индексация закончилась; проверка проблем раз в час; очистка по
сроку хранения раз в неделю; учебное восстановление раз в месяц;
инкрементальная индексация ночью.

Своего демона в системе нет намеренно — он был бы ещё одним процессом,
который может тихо умереть. Используется crontab на Linux и macOS,
планировщик задач на Windows.

### 19.3. Учебное восстановление

Проверка при создании копии смотрит, что архив цел. Учебное
восстановление проверяет другое: что развёрнутый из копии индекс
действительно ищет. Копия разворачивается целиком во временную папку, и
по ней прогоняются контрольные вопросы. Это разные вещи, и вторая
обнаруживает то, чего первая не видит.

### 19.4. Проверка качества после переиндексации

Контрольные вопросы прогоняются автоматически после полной
переиндексации и после пересчёта векторов. Если качество упало заметно,
об этом пишется прямо в карточке задачи, а не обнаруживается через месяц
по жалобам. Без набора контрольных вопросов шаг молча пропускается —
и это, пожалуй, лучший довод в пользу того, чтобы его наконец собрать.

## 20. Запуск в продакшне

Раздел про то, что отличает «работает у меня» от «работает у компании».
Всё перечисленное найдено сплошной проверкой кода и исправлено; здесь
описано, как оно устроено теперь и что от вас требуется при разворачивании.

### 20.1. Проверка перед стартом

Каждый процесс — админка, бот, индексация — перед началом работы
проверяет, можно ли вообще работать с такой настройкой, и печатает
результат. Проверки двух видов, и разделение здесь важнее самих проверок.

**Не запускаемся** при том, при чём работа невозможна или опасна: некуда
писать данные, повреждён индекс, админка открыта наружу без всякой
защиты, роль по умолчанию не описана в разграничении доступа. Молча
продолжить в таких случаях хуже, чем не подняться: упавшая служба видна
сразу, а тихо открытая наружу админка не видна никому.

**Предупреждаем и работаем** при том, что ухудшает качество, но работать
не мешает: не обучена модель смыслового поиска, пуст индекс, не
распознаны сканы, в качестве модели стоит заглушка. Останавливаться
из-за этого нельзя: ассистент, отвечающий хуже, всё равно лучше
ассистента, который не отвечает.

```bash
python preflight.py                # проверить настройку
python preflight.py --role бот     # то, что важно именно боту
python preflight.py --strict       # считать предупреждения ошибками
```

До этого любой процесс поднимался при какой угодно настройке. Папки базы
знаний не существует — админка запускается, systemd показывает `active`,
всё выглядит исправным, и первым о поломке узнаёт сотрудник, задавший
вопрос.

### 20.2. Корректная остановка

Систему останавливают буднично и часто: обновление, перезапуск
контейнера, ночная перезагрузка сервера. Теперь каждый процесс
обрабатывает сигнал остановки: перестаёт брать новую работу, дописывает
начатое и выходит. Индексация прерывается на границе файла и сообщает,
сколько успела; следующий запуск продолжит с этого места.

Отдельно про контейнер. Python внутри становится процессом номер один, а
для процесса номер один ядро не применяет действие по умолчанию — сигнал
остановки просто игнорируется. Без обработчика `docker stop` каждый раз
ждал десять секунд и убивал процесс насмерть. То есть повреждение
индекса «при аварии» на самом деле происходило при каждом штатном
обновлении. В `docker-compose.yml` задан запас времени
(`stop_grace_period`), в юните systemd — `TimeoutStopSec`.

### 20.3. Файлы, которые нельзя увидеть наполовину записанными

Индекс векторов, модель смыслового поиска, файл настроек, файл ключей и
список учётных записей пишутся через временный файл с последующим
переименованием. Переименование внутри одной файловой системы атомарно:
на диске всегда лежит либо старое содержимое целиком, либо новое
целиком.

Это не теория. Обрезанный файл векторов система читала молча и обнуляла
индекс — смысловой поиск исчезал, а работа продолжалась. Обрезанный
файл учётных записей читался как «записей нет», и вход по паролю тихо
выключался. Обрезанный `.env` возвращал систему к значениям по
умолчанию, то есть к другой папке базы и другому провайдеру модели.
Теперь повреждение обнаруживается и попадает в журнал и в диагностику, а
не растворяется.

Резервная копия пишется под временным именем и переименовывается в
конце. Иначе обрыв посреди упаковки оставлял обрезанный архив с
правильным именем и свежей датой: список копий показывал его как
последнюю удачную, а правило хранения удаляло ради него предыдущую
нормальную.

### 20.4. Одна очередь на все процессы

Регулярные задания запускаются через `runjob.py`, а не прямым вызовом
модуля. Разница принципиальная: прямой вызов `index.py update` из cron —
это отдельный процесс, ничего не знающий о блокировках. Ночной проход и
нажатая в админке переиндексация писали в один и тот же файл векторов,
каждый из своей копии в памяти, и побеждал сохранивший последним. Часть
работы пропадала, ошибки при этом не было — индекс выглядел целым.

Восстановление из копии тоже идёт через очередь, а не прямо в
обработчике запроса: оно сначала отодвигает текущие данные и только
потом раскладывает новые, и обрыв между этими шагами оставлял систему
вообще без индекса.

Обработчик очереди поднимается вместе с процессом админки. Раньше он
запускался только по нажатию кнопки, поэтому задача, поставленная на
повтор и пережившая перезапуск, не выполнялась никогда, а занятый ею
ресурс оставался занятым.

### 20.5. Что настроить при выставлении наружу

Порядок действий, если админка должна быть доступна не только с сервера.

1. Завести учётные записи: `python security.py adduser`. Общий токен —
   мера временная, роли он не различает.
2. Поставить перед админкой обратный прокси с TLS и включить
   `ADMIN_TRUST_PROXY=1`.
3. Убедиться, что ключи лежат в защищённом файле, а не в `.env`:
   раздел «Безопасность», кнопка «Вынести ключи».

Второй пункт — самое важное место во всей настройке, и раньше оно было
ловушкой. Когда прокси стоит на той же машине, адресом клиента для всех
запросов снаружи становится `127.0.0.1`, а значит правило «с локального
адреса можно всё» открывало админку без пароля всему интернету — причём
именно в той схеме, которую сами же и рекомендуем. Теперь при
`ADMIN_TRUST_PROXY` настоящий адрес берётся из заголовка прокси, а
проверка перед запуском не даст подняться с этой настройкой без
заведённых учётных записей.

Заголовкам прокси система верит только при этом флаге. Иначе любой
клиент объявляет свой запрос локальным и защищённым, а имя в журнале
действий подставляется одной строкой curl — журнал аудита, ради которого
всё и заводилось, подделывался бы тривиально.

### 20.6. Что защищает от перебора и подделки

Подбор пароля упирается в счётчик неудачных попыток, а не в задержку.
Задержка не работала совсем: сервер многопоточный, и сотня
одновременных соединений давала сотню попыток в секунду, сколько ни спи
внутри каждой. Считается и по учётной записи, и по адресу — иначе
достаточно менять логин на каждой попытке.

Запросы, меняющие состояние, принимаются только с заголовком
`Content-Type: application/json`. Обычная HTML-форма такой заголовок
поставить не может, а запрос из скрипта на чужом сайте с ним требует
разрешения, которого мы не даём. Без этой проверки страница, открытая
администратором в соседней вкладке, могла отправить восстановление
индекса от его имени: у режимов «общий токен» и «только с локального
адреса» куки нет вовсе, там авторизует сам факт запроса с этой машины.

Общий токен принимается заголовком или куком, но не в адресе страницы.
Из ссылки он берётся ровно один раз — при открытии, где сразу
перекладывается в кук, а адрес очищается: иначе токен оседает в журнале
прокси, в истории браузера и в заголовке `Referer` при первом же
переходе по внешней ссылке.

### 20.7. Что не попадает в журналы и копии

Значения ключей не пишутся в журнал действий. Журнал лежит в основной
базе, а база — первым файлом в резервной копии: один архив, переданный
подрядчику, означал бы передачу всех ключей компании. В журнале
остаётся, что ключ меняли и когда, но не на что.

Маскирование в журналах теперь распространяется и на подставляемые
значения, а не только на текст сообщения. Весь код пишет
`log.error("…: %s", exc)`, поэтому секрет из текста исключения ложился в
журнал как есть — так утекал пароль АТС, который входит в адрес
подключения. Журналы при этом доступны любой роли админки, включая
«только смотреть».

### 20.8. Разграничение доступа, которое нельзя обойти

Три обхода, которые существовали и закрыты.

Роль, не описанная в `ROLE_SECTIONS`, получала доступ ко **всему**:
фильтр просто не применялся. Хватало опечатки — «Sales» вместо «sales»,
роль, выданная в админке с другой раскладкой. Теперь наоборот: если
разграничение настроено, а роль в нём не описана, выдача закрыта
целиком и об этом пишется в журнал. Пустую выдачу заметят в тот же день,
утечку не заметит никто.

Цены роль не смотрели вовсе. Поскольку позиции прайса подставляются в
ответ отдельным блоком с пометкой «точные данные», проверка ответа на
утечку их тоже не видела — она смотрела только на фрагменты документов.
Весь контур разграничения обходился вопросом «сколько стоит артикул
такой-то». Теперь цены фильтруются тем же кодом, что и документы, а
проверка утечки смотрит и на них.

Кнопка «Файл» в Telegram не проверяла ничего. Нажатие кнопки — отдельный
запрос с произвольным содержимым, который отправляется любым клиентом, не
видя ни кнопки, ни сообщения: `doc:1`, `doc:2`, … выгружали любой
документ базы, и это работало даже у заблокированного сотрудника. Теперь
доступ проверяется заново при каждом нажатии, а ответ для закрытого
раздела не отличается от ответа для несуществующего документа — иначе
перебор номеров показывает, что там что-то есть.

Отдельно: очередь заданий — это второй вход к тем же действиям.
Восстановление индекса закрыто на своём эндпоинте, но точно так же
запускалось через постановку задачи. Разграничение, у которого есть
обходной путь, не разграничивает ничего.

### 20.9. Обновление, когда репозиторий и установка в разных папках

Обычный случай: код склонирован в одну папку, а работающая установка
живёт в другой — например, репозиторий в `~/rag2`, а установка в
`~/kb-assistant`. Запущенный из клона `update.sh` раньше молча брал ту
папку, из которой его запустили: делал в ней `git pull` (в клоне это
всегда «уже актуально»), а затем падал на отсутствующем окружении
Python сообщением `No such file or directory`. По этому сообщению
невозможно догадаться, что обновлялась вообще не та папка.

Теперь скрипт сначала проверяет, что перед ним установка — то есть
папка, где есть и окружение Python, и `webui.py`. Если это не так, он
ищет установку в обычных местах, а не найдя, объясняет, что произошло, и
печатает готовую команду:

```bash
./update.sh --target ~/kb-assistant --from ~/rag2
```

`--from` копирует только код: данные, журналы, окружение, `.env` и файл
ключей установки остаются нетронутыми. Это важнее, чем кажется — без
такого исключения обновление затирает рабочие настройки файлом из
репозитория.

Ещё две вещи, которые изменились по той же причине «не оставлять
установку в промежуточном состоянии». Сбой установки библиотек больше не
прерывает обновление: к этому моменту код уже скопирован, а причина
почти всегда внешняя и временная — нет сети, закрыт индекс пакетов,
отвалилось зеркало. Вместо отката печатается предупреждение с командой,
которой это повторяют потом. Проверка загрузки модулей тоже стала
диагностикой, а не условием: она перечисляет то, что не загрузилось, но
не откатывает обновление целиком, потому что чаще всего не хватает
необязательной библиотеки для одного формата файлов.

### 20.10. Кто заметит, что система умерла

Мониторинг устроен по правилу «отказавший детектор отказов — самый
опасный отказ», поэтому у каждой проверки есть дублёр.

Бот и админка раз в минуту отмечаются в телеметрии («пульс»). Проверка
оповещений сравнивает отметку с часами: бот, убитый ночью нехваткой
памяти, обнаруживается за десять минут, а не через неделю по жалобам
сотрудников. При установке с ключом `--service` бот получает собственную
службу (`kb-assistant-bot` в systemd, отдельный агент в launchd) с
безусловным перезапуском.

Сами проверки оповещений запускаются двумя независимыми путями: по
расписанию cron и из вечно живого потока админки (настройка
`ALERTS_SELF_CHECK_MINUTES`, по умолчанию раз в час). Снесённый при
миграции crontab больше не превращает мониторинг в молчание,
неотличимое от «всё хорошо».

Свободное место проверяется на всех разделах, где живут данные,
журналы, копии и распаковки, — а не только на разделе с данными.

### 20.11. Копии, которые переживут отказ диска

По умолчанию копии лежат в `data/backups` — на том же диске, что и
данные. Отказ диска в такой конфигурации уносит и данные, и все копии:
ровно то, от чего копии должны защищать. Поэтому проверка перед стартом
и оповещения напоминают о настройке `BACKUP_MIRROR_DIR` — сетевой папке
или внешнем диске, куда каждая копия дублируется. Задайте её до запуска
в продакшн; оповещение «зеркало устарело» сработает, если дублирование
перестанет работать.

При откате обновления (`update.sh --rollback`) возвращаются код и
настройки, но не база данных: если обновление мигрировало схему вперёд,
старый код упадёт не в момент отката, а позже, на первом обращении к
изменённой таблице. Скрипт отката печатает об этом предупреждение и
команду восстановления данных из снимка, сделанного тем же обновлением.

### 20.12. Точность ответа как контур, а не как надежда

Ответ модели проверяется по результату. Ссылки на источники сверяются со
списком: номер [7] при трёх источниках вырезается. Числа из ответа
ищутся в переданных фрагментах: не найденные не удаляются (модель могла
законно пересчитать), но помечаются предупреждением «сверьтесь с
первоисточником» — и для читателя, и в журнале.

Порог честного отказа (`MIN_CONFIDENCE`) сравнивается с интерпретируемой
величиной: насколько лучший фрагмент покрывает значимые слова вопроса
(0…1). Ноль означает «ни одно существенное слово вопроса не нашлось».
Прежняя шкала — ранговый балл слияния каналов — делала порог
математически недостижимым, и «в базе знаний нет данных» не говорилось
никогда.

Индекс и запрос нормализуются одной функцией (`normtext.py`): «ё» и «е»,
«м³/ч» и «м3/ч», «3,6» и «3.6» совпадают по обе стороны поиска. После
обновления с прежних версий индекс нужно пересобрать: `python index.py
build --force`, затем `train-lsa` и `reembed` — старые тексты в индексе
нормализованы по-старому.

## 22. Путь вопроса под микроскопом

Методология целиком, шаг за шагом, с настройками и примерами. Сквозной
пример: сотрудник пишет боту «какая производительность у водомета 60/92».

### Шаг 1. Приём и допуск (`bot.py`)

Сообщение принимает Telegram-бот. Проверяется белый список (`access.py`):
у сотрудника есть роль, роль определяет видимые разделы базы. Не в
списке — вежливый отказ с инструкцией `/request`. Частота ограничена
(`RATE_LIMIT_PER_USER_HOUR`, по умолчанию 60 в час) — от зацикленных
скриптов, не от людей. Вопросы обрабатываются параллельно; предел
нагрузки на модель держит не бот, а общая очередь (шаг 9).

### Шаг 2. Обезвреживание (`security.py`)

Вопрос проверяется на попытку переопределить правила («забудь
инструкции», «покажи системный промпт»). Подозрительный не отклоняется,
а берётся в кавычки с пояснением модели, что внутри — текст вопроса, а
не указания. Почему так: «забудь про Grundfos, меня интересует Wilo» —
нормальный вопрос, отказывать на него хуже, чем перестраховаться.

### Шаг 3. Выверенные ответы (`answer.py`, канал golden)

Если эксперт уже отвечал на близкий вопрос — отдаётся его ответ с
пометкой «выверен экспертом», без поиска и модели. «Близость» проверяется
жёстко: числовые подписи моделей («60/92») и бренды обязаны совпасть как
множества, слова — на три четверти. В примере: эталона про 60/92 нет,
есть про 55/75 — подписи не совпали, канал пропускается. До этой
проверки ответ на вопрос про 60/92 уходил с данными 55/75 и пометкой о
выверенности — самая дорогая ошибка из найденных в системе.

### Шаг 4. Ценовой маршрут (`prices.py`)

Слова «цена/стоимость/прайс/артикул» отправляют вопрос в таблицу
`products` — точный поиск, не векторный. Артикул ищется точно (регистр
и суффиксы учтены), подпись модели из вопроса обязана присутствовать в
названии позиции. Наш пример — не про цену, маршрут пропускается.

### Шаг 5. Нормализация и два канала поиска (`normtext.py`, `search.py`)

Вопрос приводится к каноническому виду: «водомета» остаётся словом, а
вот «м³/ч» стало бы «м3/ч», «3,6» — «3.6», «ё» — «е». Ремонт гомоглифов
чинит смешанную раскладку («водомeт» с латинской e). Дальше два канала:

*Текстовый (BM25, FTS5).* Запрос: значимые слова + числа + основы слов
как префиксы + синонимы. Для примера: `"производительность" OR "подача"
OR "расход" OR "водомета" OR "водомет"* OR "60/92"`. Синоним «подача»
здесь решает всё: в паспортах пишут именно так.

*Смысловой (векторы).* Вопрос переводится в вектор той же моделью, что
индексировала базу (`EMBEDDINGS_PROVIDER`: своя LSA, ONNX или облако), и
ищутся близкие фрагменты. Канал ловит перефразировки, которых нет в
тексте дословно.

### Шаг 6. Слияние и свежесть (`search.py`)

Списки объединяет Reciprocal Rank Fusion: балл зависит от места в каждом
списке (`RRF_K`). К баллу подмешивается свежесть документа
(`RECENCY_ALPHA`, `RECENCY_HALF_LIFE_DAYS`): при равной релевантности
свежий прайс выигрывает у позапрошлогоднего. Устаревшие версии
(вытесненные более новой) в выдачу не попадают вовсе. Фильтр ролей
отсекает недоступные сотруднику разделы — и если роль неизвестна,
закрывается всё (ошибка в безопасную сторону).

### Шаг 7. Переранжирование (`rerank.py`)

Первые `RERANKER_TOP_N` кандидатов перечитываются парой «вопрос +
фрагмент» и переоцениваются. По умолчанию — лексический оценщик без
моделей: покрытие редких слов вопроса, кучность, совпадение артикула.
Оценка не подменяет балл поиска, а смешивается с ним (`RERANKER_WEIGHT`).
Сбой или таймаут реранкера — выдача в исходном порядке, ответ не
теряется.

### Шаг 8. Порог честного отказа (`search.confidence`)

Считается релевантность лучшего фрагмента — покрытие значимых слов
вопроса, от 0 до 1. Ниже `MIN_CONFIDENCE` (0.08) — бот отвечает «в базе
знаний нет данных», записывает вопрос в пробелы и предлагает эксперту
ответить. В примере фрагмент паспорта 60/92 покрывает и «водомет», и
«60/92», и «подачу» — релевантность ~0.7, порог пройден.

### Шаг 9. Очередь к модели (`llm_queue.py`)

Место в очереди берётся до обращения к модели. Приоритеты: звонок и
голосовое — вперёд (человек ждёт на линии), обычный вопрос — следом,
фоновая обработка базы — в конец. `LLM_MAX_CONCURRENT` (по умолчанию 1)
— сколько запросов модель обслуживает одновременно; для одной
видеокарты больше и не нужно. Переполнение очереди — честный отказ с
показом найденных фрагментов.

### Шаг 10. Контекст и генерация (`answer.py`, `llm.py`)

Фрагменты нумеруются: сначала прайсы (если были), затем документы;
дубли выбрасываются; общий объём ограничен `CONTEXT_MAX_CHARS`. Промпт
требует: отвечать только по фрагментам, ставить [n] после каждого
утверждения, характеристики переносить дословно, при противоречии
верить более свежему документу. Провайдер с ретраями на перегрузку и
пустой ответ; сбой основного — переход к запасному с записью в журнал.

### Шаг 11. Проверка ответа по результату (`answer.verify_answer`, `security`)

Ссылки: [7] при трёх источниках вырезается. Числа: «92 м» должно
встречаться во фрагментах — не найденные числа помечаются «сверьтесь с
первоисточником». Утечка: если в ответ попал раздел, закрытый роли, —
весь ответ заменяется отказом. Только после этого текст уходит
сотруднику — с нумерованными источниками и кнопками 👍/👎 и «Файл».

### Шаг 12. След (`_log_query`, `tracing.py`, `metrics.py`)

Записывается всё, из чего потом собирается аналитика: вопрос, ответ,
источники со баллами, стадия («ответил» / «нет данных» / «модель
недоступна»), задержка, токены. Плохая оценка 👎 уводит вопрос в задачи
экспертам; трассировка позволяет разобрать любой конкретный ответ по
шагам («Запросы» → «разбор»).

## 23. Профили настройки под типовые конфигурации

Готовые сочетания настроек. Каждый профиль — это строки для `.env`
поверх умолчаний; всё остальное трогать не нужно. После правки .env
перезапуск не обязателен: настройки перечитываются на лету.

### 23.1. Ноутбук или офисный компьютер без видеокарты

Всё локально, но без тяжёлых моделей: поиск полноценный, генерация — в
облаке (или заглушка, пока облако не подключено).

```bash
KB_ROOT=/путь/к/BD
EMBEDDINGS_PROVIDER=lsa          # своя модель, обучается на вашей базе
RERANKER_PROVIDER=lexical        # без нейросетей, работает всегда
LLM_PROVIDER=gigachat            # или yandex; ключ — в файле ключей
LLM_FALLBACK=echo                # облако недоступно — показать фрагменты
OCR_PROVIDER=tesseract           # сканы распознаются процессором, медленно
```

Ожидания: индексация 100 ГБ — ночь; ответ 3–8 секунд (зависит от
облака); сканы — по несколько секунд на страницу, запускайте на ночь.

### 23.1а. Mac с Apple Silicon: модели на встроенной видеокарте

Единая память мака работает как видеопамять (Metal); система считает
доступной примерно две трети общей. vllm на macOS не работает — модели
запускаются через ollama; установщик и `update.sh` ставят его сами
(на маке через brew, на Linux — официальным скриптом ollama.com,
на Windows — через winget; выключается общим `--no-packages`). Дальше как
обычно: раздел «Модели» → выбрать модель с тегом ollama (Qwen3.6 27B,
Qwen3.6 35B, Gemma 3) → «Запустить». На 32 ГБ памяти уверенно работает
Qwen3.6 27B; на 16 ГБ берите модели до 10 ГБ.

```bash
LLM_PROVIDER=local               # адрес ollama подхватится сам
EMBEDDINGS_PROVIDER=lsa          # или onnx — тоже работает на маке
RERANKER_PROVIDER=lexical
```

Если ollama уже запущен как приложение (иконка в строке меню), система
это увидит и второй сервер поднимать не станет.

### 23.2. Сервер с одной видеокартой 24 ГБ

Локальная генерация, всё внутри компании. Самый частый продакшн-профиль.

```bash
KB_ROOT=/data/BD
LLM_PROVIDER=local
LOCAL_LLM_MODEL=t-pro-2.0        # python models.py serve t-pro-2.0
LLM_FALLBACK=gigachat            # облако на случай падения сервера модели
EMBEDDINGS_PROVIDER=onnx         # USER-bge-m3, готовится один раз
ONNX_MODEL_PATH=/opt/user-bge-m3-onnx
RERANKER_PROVIDER=onnx
LLM_MAX_CONCURRENT=1             # одна карта — один запрос, иначе все медленно
OCR_PROVIDER=vlm                 # сканы через ту же модель, очередь общая
```

Модель занимает ~22 ГБ; эмбеддер и реранкер помещаются рядом. Если
тесно — `qwen3-14b` (10 ГБ) или `gigachat3-20b-a3b` (14 ГБ).

### 23.3. Две карты по 24 ГБ

Первая — генерация, вторая — всё остальное (эмбеддинги, распознавание
речи, синтез, OCR). К профилю 23.2 добавьте:

```bash
VOICE_STT_PROVIDER=whisper       # распознавание речи локально
ASR_DEVICE=cuda:1                # расшифровка видео — на второй карте
VOICE_TTS_PROVIDER=silero        # синтез локально
LLM_MAX_CONCURRENT=2             # смесь экспертов тянет два потока
```

### 23.4. Только облако, минимум своего железа

```bash
LLM_PROVIDER=gigachat
LLM_FALLBACK=yandex              # два независимых облака надёжнее одного
EMBEDDINGS_PROVIDER=lsa          # векторы всё равно лучше считать у себя:
                                 # облачные эмбеддинги дороги на переиндексации
RERANKER_PROVIDER=lexical
```

Помните: вопросы сотрудников и фрагменты документов уходят провайдеру.
Прочитайте его условия обработки данных; ключи держите в файле ключей
(раздел «Безопасность» → «Вынести ключи»).

### 23.5. Максимальная приватность: наружу не уходит ничего

```bash
LLM_PROVIDER=local
LLM_FALLBACK=                    # пусто: лучше отказ, чем утечка
EMBEDDINGS_PROVIDER=onnx         # модель скачана заранее, работает офлайн
RERANKER_PROVIDER=onnx
OCR_PROVIDER=vlm                 # или tesseract
VOICE_STT_PROVIDER=whisper
VOICE_TTS_PROVIDER=silero
CRAWL_MAX_PAGES=0                # не ходить по внешним сайтам
```

Проверка, что снаружи действительно ничего нет: `python preflight.py` и
раздел «Диагностика» показывают, какие провайдеры куда обращаются.

### 23.6. Пилот на месяц: минимум усилий

Ставьте умолчания как есть (`./install/install.sh`), укажите KB_ROOT,
пройдите «Быстрый старт». Единственные две вещи, которые стоит сделать
даже в пилоте: сменить пароль admin и указать BACKUP_MIRROR_DIR на
сетевую папку — выверенные ответы экспертов невосстановимы.

## 24. Как пользоваться справочником параметров

Всех настроек — 213, и все описаны в `НАСТРОЙКИ.md` (генерируется из
кода: `python settings_schema.py md > НАСТРОЙКИ.md`, поэтому разойтись с
реальностью не может). У каждой: назначение, рекомендация, пример,
умолчание и допустимый диапазон. Те же карточки — в админке, в разделе
«Настройки» и внутри тематических разделов.

Куда смотреть в первую очередь — десять настроек, которые реально
крутят под себя, остальные двести три можно не трогать годами:

| Настройка | Зачем крутить |
|---|---|
| `KB_ROOT` | путь к базе знаний — единственная обязательная |
| `LLM_PROVIDER` + `LLM_FALLBACK` | кто отвечает и кто подстраховывает |
| `EMBEDDINGS_PROVIDER` | качество смыслового поиска; после смены — reembed |
| `RERANKER_PROVIDER` / `RERANKER_WEIGHT` | точность топа выдачи; выбирать замером (§10.3) |
| `MIN_CONFIDENCE` | граница «отвечаем/честно молчим»; поднимать по контрольным вопросам |
| `ROLE_SECTIONS` + `DEFAULT_ROLE` | кто какие разделы видит; настроить до запуска наружу |
| `LLM_MAX_CONCURRENT` | по числу того, что реально тянет карта |
| `RECENCY_HALF_LIFE_DAYS` | насколько быстро устаревают документы (прайсы — быстро) |
| `BACKUP_MIRROR_DIR` | копии, которые переживут отказ диска |
| `CONTEXT_MAX_CHARS` | под окно вашей модели: маленькой модели — меньше |

Правило безопасного изменения: одно значение за раз → прогнать
контрольные вопросы (раздел «Контрольные вопросы» → «Прогнать поиск»)
→ сравнить с прошлым замером в истории. История хранит слепок настроек
каждого замера, поэтому на вопрос «после чего стало хуже» всегда есть
точный ответ, а не воспоминания.
